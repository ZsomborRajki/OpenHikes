# Files the coverage floor does not measure.
#
# Every path here is a file whose executable lines are SwiftUI body code, and
# body code is evaluated by exactly one suite: OpenHikesUITests. That suite is
# deliberately not run in CI — it drives a simulator through real gestures and
# timing-sensitive waits, which a shared runner makes slow and unreliable; see
# the note at the foot of .github/workflows/ci.yml. So in the job that measures
# coverage these files can only ever read as untested, however well tested the
# screens actually are.
#
# Leaving them in the denominator made the gate measure the wrong thing. The
# number fell as screens were added, whatever the tests did: over the two days
# before this list was written the app gained 2352 executable lines and 508
# covered ones, and the percentage dropped 1.87 points while not one suite was
# deleted or weakened. A gate that goes red for shipping a screen is a gate
# people learn to lower, which is the one change the floor exists to prevent.
#
# What is left after these exclusions is the code the unit suites can actually
# reach, and it is held to a floor worth having — around 79% when this list was
# written, against 55% for the whole target. A real fall there is a suite
# deleted or a domain stubbed out, which is what the gate is for.
#
# Two rules keep this list honest:
#
#   1. A path that matches no file in the report fails the gate. A screen that
#      is renamed or deleted has to be spelled here again, so the list cannot
#      quietly rot into an exemption for code nobody meant to exempt.
#
#   2. Nothing here is measured, including a non-view type that later grows
#      inside one of these files. Several already carry a small one — the
#      metrics constants in HikeDetailComponents, the segment enum in
#      HikeDetailView, the disclosure text in CommunityShareSheet and its
#      sibling in CommunityPhotoShareSheet, the resting page index in
#      CommunityPhotoViewer — and where that logic is worth
#      pinning it has its own suite, which goes on running either way. Logic
#      that grows past a handful of lines belongs in its own file, where the
#      floor can see it again.
#
# Five paths here arrived from the two duplication sweeps of 2026-09-19 and
# 2026-09-20, and they are the case rule 2 above describes running in reverse.
# Folding a section that two screens drew identically — a breakdown bar, a
# review strip, a mail ending, a gallery chevron, a sent section — produces a
# new file that is *entirely* body code. Inside the two screens those lines
# were already exempt, because the screens are; extracted, they landed in the
# denominator as permanently uncovered and took the measured number down 0.82
# points across the two sweeps without one suite being weakened. Deduplicating
# a screen is not a fall in what this gate is for.
#
# The rule that keeps it honest is the same one: what comes out of a screen and
# is *not* body code does not belong here. CommunitySharePhotoTally came out of
# the same fold and has its own file and its own suite, and
# PhotoCalloutPreviewControl is UIKit the unit suites already reach at 94%.
#
# Eight more paths arrived on 2026-09-21, and they are the same case again
# rather than a new one: screens and folded-out sections written after this
# list was, which nobody added to it. They took the measured number to 75.21%
# and turned the gate red on a `main` whose suites were all green — the first
# time this gate has failed for the reason the list exists to prevent. Two
# files that turned up in the same sweep are deliberately *not* here:
#
#   * `CommunityShareButtonAppearance` is a value type with `import Foundation`
#     and no view in it, working out one toolbar button's glyph, label and hint
#     from three states. It is the precedence its own header calls too subtle
#     to write three times, so it is exactly what the floor should be
#     measuring; `CommunityShareButtonAppearanceTests` now covers it.
#   * `CameraPicker` is a `UIViewControllerRepresentable` and its coordinator —
#     UIKit glue, the same kind of code as PhotoCalloutPreviewControl above,
#     and reachable in principle by the unit suites.
#
# `OpenHikesView+Photos` is the honest borderline: an extension on a `View`
# whose members are `func`s that attach a photograph rather than body code. It
# stays measured, because the rule at the top of this file is about what the
# lines *are* and not about which type they hang off.
#
# Two arrived with the trail maker on 2026-09-21, and they are the
# ordinary case rather than a new one: `TrailDraftView` is the maker's screen,
# and `TrailDraftFields` is the three small `View`s it is built from — both
# entirely body code that only `OpenHikesUITests` evaluates. A third,
# `TrailDraftActions`, was the edit menu, and it went with the menu. The rest of
# `Hikes/Maker/` is deliberately *not* here and is exactly what this gate
# should be measuring — the draft's arithmetic, the controller's guards, the
# store's one-row rule and the save that writes a `Hike`, each with a suite of
# its own — and neither is `MapTrailDraftControls` or `MapTrailDraftOverlay`,
# which are UIKit and MapKit the unit suites reach through
# `MapCoordinatorTests+TrailDraft`.
#
# `HikePlaceSection` arrived with its Phase 4 on 2026-09-21, and it is the same
# case: the read-only list of a saved hike's marked places. `TrailPlace`,
# `TrailPoint` and `MapTrailPlaceAnnotations` are deliberately *not* here: the
# first two are arithmetic and a model, and the third is MapKit the unit
# suites reach through `MapCoordinatorTests+TrailPlaces`.
#
# The maker's own place editor, place list and nearby section went when the
# maker moved to Apple Maps' place sheet, and their entries went with them.
# `TrailPlaceSheet`, which replaced them, stays measured: it carries
# `TrailPlaceCard` and `TrailPlaceCoordinates` alongside its views, and the
# rule at the top of this file is about what the lines are.
#
# The UI suites still exist and still run locally:
#
#   Scripts/run-ui-tests.sh --all
